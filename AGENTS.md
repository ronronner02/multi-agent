## Language and Governance Policy
**Language setting:** `English / 英文`
Language rules are an absolute hard-execution requirement: unless the current request explicitly asks for another language, translation, bilingual output, or preserved source text, all newly generated natural-language content intended for the user must be in English.
Scope covers responses, status updates, clarification questions, summaries, reviews, generated documents, requirements, plans, tasks, change notes, commit messages, and PR text.
Code identifiers, commands, paths, config keys, environment variables, API names, protocol names, logs, tool output, and quoted material may remain in their original language; any new explanation, conclusion, or surrounding guidance must follow this language setting.
The source language of skills, agents, templates, historical context, or examples must not override this setting; new code comments also follow this setting and explain only non-obvious intent.
### External Output Privacy and Attribution
Never automatically add workflow, tool, skill, agent, model, vendor, or generation-method names, attribution, links, footers, badges, or promotional text to newly generated user-facing or external artifacts, including pull requests, issues, commits, release notes, changelogs, reports, plans, specifications, and business documents.
Never automatically add `Built with`, `Generated by`, `Powered by`, AI authorship, or co-author trailers. Add a specific attribution only when the user explicitly requests that exact attribution in the current turn.

## Execution Rules for Agents

These rules apply to every agent that implements tasks in this repository, attended or unattended. The plan in `docs/plans/` owns scope and decisions; these rules govern how the work is run.

### Environment
- The only development checkout is WSL Ubuntu `/home/leo/src/multi-agent` (`\\wsl.localhost\Ubuntu\home\leo\src\multi-agent` from Windows). Never edit `D:\Multi-Agent`; it must stay byte-identical to the cutover manifest.
- Run every build, test and git command inside WSL with `export PATH=/opt/multi-agent/toolchain/node/bin:$PATH`. On Windows, launch tools from PowerShell, not Git Bash, which mangles UNC paths.
- Always detach stdin (`</dev/null`) for test runs. A vitest run attached to a terminal gets suspended and hangs forever.
- Memory is limited:
  - Run one vitest process at a time.
  - Use `--maxWorkers=2` for focused runs and `--maxWorkers=4` for a full package suite.
  - Before you finish, make sure `pgrep -f vitest` returns nothing.

### Starting a task
- Work from the task pack in `docs/tasks/`. First run `spec-first tasks validate <task-pack> --repo /home/leo/src/multi-agent --json`. If it reports source-plan drift, regenerate the pack from the current plan before executing any task. Never execute a stale card.
- Do one task at a time. Before writing anything, compare the current source with the task's test scenarios. Work that already satisfies a scenario is verified and recorded, not rewritten.
- The task's Files list is the scope budget. A file outside the list may join only when direct evidence shows it completes this task. When a change affects acceptance, a public contract, architecture or source ownership, stop and report it as a plan question.

### Fixing the right way
- Fix a defect at the owner that the cited KTD names, not at each call site. If a fix would add the same guard to many call sites, stop and report it; that is a design question for the plan owner, not more implementation.
- Do not fix pre-existing problems that the task does not need.
- A failing test is pre-existing if it also fails at the task's base commit. To check, run it in a throwaway `git worktree` at that commit, with `node_modules` symlinked from the main checkout; remove the worktree afterwards. Record pre-existing failures and fix only failures the task caused.
- Never weaken a legacy test to make it pass. Legacy mode must behave exactly as before.

### Bounded loops and stop conditions
- Make at most two fix-and-rerun cycles per failing check. Each task gets two review rounds, under the plan's Review convergence rule; after round 2, P2/P3 findings become recorded residuals. Rounds 3 and 4 run only for open P0/P1 findings, and only while the progress gate holds: the open P0/P1 count is strictly lower than after the previous round, and no P0/P1 fixed earlier reappears. Those rounds fix only the open P0/P1 findings. When the gate fails, or a P0/P1 is still open after round 4, the task goes back to the plan owner. When the plan owner records a fix decision for that P0/P1, implement only the decided fix, refresh the candidate and rerun verification; the fix gets one further review round, and a P0/P1 that survives it goes back to the owner again.
- **Task-level budget (owner rule, 2026-10-19).** The limits below apply to the whole task, summed over every slice, run and session. They never reset when a session resumes, compacts or restarts.
  - A task gets at most 3 `spec-work` runs, 6 edit slices and about 1,200 changed lines.
  - A task gets at most one scope amendment. A second needed amendment means the task is too large: stop and propose a split to the plan owner.
  - Review rounds count per task, not per slice. A slice-level review uses one of the task's rounds, so prefer one review of the task candidate over a review of every slice.
  - When the next slice would exceed a limit, stop before starting it. Record what is done and reviewed, then hand the remainder back as a split proposal.
  - The budget applies to T037, T038 and every task not yet started. T010's closeout follows the owner-decided terms in the plan's T010 owner split.
- When a done signal depends on a production component, owner or composition path that does not exist yet and is not a named slice of the task, stop and report it as a plan question. Do not prepare a scope amendment to absorb it.
- A resumed or compacted session reuses recorded evidence whose source hashes still match. It does not rerun those checks or re-review an unchanged candidate.
- When running unattended, do not ask questions. Take the most conservative option these rules allow, record it, and continue.
- Stop and report rather than improvise when:
  - the plan conflicts with the current source;
  - a fix needs an out-of-scope file that affects architecture or a contract;
  - a required tool or credential is missing;
  - a P0/P1 finding fails the progress gate or survives round 4;
  - the task-level budget above is reached.

### Review and verification cost
These rules size review and verification to the change. They take precedence over a workflow skill's default review shape, and they never lower a task's done signal or required review gate.
- **Reviewer roster (owner rule, 2026-10-19).** Every required review uses exactly two report-only reviewers on the same frozen candidate:
  - `gpt-6.1-sol`;
  - `ds/gpt-6-astra`, the owner's DeepSeek-backed mapping. The gateway requires the `ds/` prefix, so always pass the full ID.

  Each reviewer covers every lens the diff selects. This replaces both the earlier one-reviewer-per-lens dispatch and the `claude-opus-5-5` reviewer. Reach both models through the locally configured gateway, never persisting or printing keys. If either model is unavailable, the review gate stays open.
  - **Reaching the reviewers:**
    - `gpt-6.1-sol` runs through `codex exec -s read-only`.
    - `ds/gpt-6-astra` supports the Responses API (owner confirmation, 2026-10-20), so it also runs through `codex exec -s read-only -m ds/gpt-6-astra`.
    - `ds/claude-*` models run only through the Claude CLI (`claude -p --model ds/claude-...`), never through `/chat/completions`.
    - **Temporary substitution (owner, 2026-10-21):** until the owner restores the DeepSeek gateway mapping, the second reviewer is `claude-sonnet-5-5`, run as a report-only subagent, in place of `ds/gpt-6-astra`. Revert to the roster above once the owner says the mapping works.
    - If that stream drops, call the gateway's `/chat/completions` endpoint directly with system and user roles only, a client `User-Agent` header and a streamed response. Set `reasoning_effort` to `low`, because the gateway ends any request at 300 seconds.
    - A read-only `codex exec` cannot read the WSL checkout. Give each reviewer frozen, read-only copies of the diff, the touched files and the contract excerpt.
    - A transport failure, such as HTTP 524 or a dropped stream, is not a review round. Retry it once.
- Pick review lenses from the diff. Correctness, testing and security always run. Adversarial runs when the diff touches authority, admission, isolation, credentials or the mailbox. Performance, reliability, maintainability, project standards, learnings, agent-native and the simplify passes run only when the diff touches what that lens checks. Record each skipped lens and the reason.
- **Review round shape (owner rule, 2026-10-22).** Later rounds confirm fixes; they do not re-review the task.
  - **Round 1 closes on both reports.** Start fixing only after both roster reviewers have reported on the same frozen round-1 candidate. Retry a reviewer that failed on transport; do not start fixes on one report.
  - **From round 2 on, the packet is the fix delta.** It holds only the delta patch against the previously reviewed candidate, the earlier rounds' findings with their dispositions, and the enclosing functions of the changed hunks. Keep it under about 40 KB. Send no full files and no base-to-head diff unless a reviewer asks for a named file. Use the lenses that raised findings plus correctness, and widen only when the fix touches files outside the earlier findings.
  - **A later round asks two questions:** is each earlier P0/P1 closed, and did the delta introduce a regression? Do not ask it to re-attack the design, re-judge dispositions or rule on the done signal; the done-signal verdict belongs to round 1 and the final candidate. A new finding from round 2 on in code the delta did not touch is recorded as a residual, unless it is a P0 with a concrete, reproduced scenario.
  - **The reviewer that raised a finding confirms it.** From round 2 on, each open finding is confirmed by the reviewer that raised it; a finding both raised needs only one. The other reviewer joins the round only when the delta touches code outside the open findings.
  - **Fixes stay minimal.** A fix round changes only what the open findings require. If closing a finding needs a new mechanism or a changed ownership model rather than a local correction, stop and raise it to the plan owner as a design question. After round 1, make no change the review did not ask for: record a defect found on the side as a residual, or, if it is a P0/P1, as a finding the next round's delta closes.
- Skip the separate final-branch review when the branch tree hash equals the reviewed candidate's; record the matching hashes. When they differ, review only the difference.
- Run the affected package suite once, on the final candidate, and rerun it only after a later source change. A failure listed in `docs/known-failures.md` with a matching test and error is pre-existing without a new base-commit reproduction; reproduce only failures the list does not cover, and add confirmed ones to it.

  - the daemon typecheck passes;
  - the focused tests pass;
  - the affected package suite has no failures the task caused.
- Write logs and a short report (changed files, results with counts, pre-existing failures, residuals, conservative choices) to `.spec-first/workflows/spec-work/multi-agent/<UTC-timestamp>-<task>/`.
- Do not edit `docs/plans/` or `docs/tasks/` while executing a task; regenerating the pack after drift is the only exception.
