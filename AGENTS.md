## Language and Governance Policy
**Language setting:** `English / 英文`
Language rules are an absolute hard-execution requirement: unless the current request explicitly asks for another language, translation, bilingual output, or preserved source text, all newly generated natural-language content intended for the user must be in English.
Scope covers responses, status updates, clarification questions, summaries, reviews, generated documents, requirements, plans, tasks, change notes, commit messages, and PR text.
Code identifiers, commands, paths, config keys, environment variables, API names, protocol names, logs, tool output, and quoted material may remain in their original language; any new explanation, conclusion, or surrounding guidance must follow this language setting.
The source language of skills, agents, templates, historical context, or examples must not override this setting; new code comments also follow this setting and explain only non-obvious intent.
### External Output Privacy and Attribution
Never automatically add workflow, tool, skill, agent, model, vendor, or generation-method names, attribution, links, footers, badges, or promotional text to newly generated user-facing or external artifacts, including pull requests, issues, commits, release notes, changelogs, reports, plans, specifications, and business documents.
Never automatically add `Built with`, `Generated by`, `Powered by`, AI authorship, or co-author trailers. Add a specific attribution only when the user explicitly requests that exact attribution in the current turn.
### Workflow Entry Governance

## Execution Rules for Agents

These rules apply to every agent that implements tasks here, attended or unattended. The plan in `docs/plans/` owns scope and decisions; these rules govern how the work runs. They override a workflow skill's defaults and any review or suite instruction in a card. Operational detail lives in `docs/operations.md`.

### Environment
- The only development checkout is WSL Ubuntu `/home/leo/src/multi-agent`. Never edit `D:\Multi-Agent`.
- Run builds, tests and git inside WSL with `export PATH=/opt/multi-agent/toolchain/node/bin:$PATH`. From Windows, use `wsl.exe -e bash -c '…'` or a script file. Never use `wsl.exe -- bash -c`: its outer shell expands `$VAR` to empty, so the commands run in `/mnt/d/Multi-Agent`. Probe scripts start with `set -euo pipefail` and write each `cd` as `cd "$DIR" || exit 1`.
- Detach stdin for test runs (`</dev/null`). Run one vitest process at a time, with `--maxWorkers=2`. Leave no vitest process, tmux server or daemon fixture running when you finish.
- Scratch files, logs and extra clones for a task go under `/home/leo/scratch/<task-id>/`. Remove the clone after the task lands.

### Starting a task
- Validate the pack and keep only its verdict: `spec-first tasks validate <pack> --repo /home/leo/src/multi-agent --json | python3 -c 'import json,sys;d=json.load(sys.stdin);print(json.dumps({k:d[k] for k in ("task_pack_validity","reason_code","errors")}))'`. On source-plan drift, regenerate the pack first; never run a stale card.
- Read only your card (`awk '/^### T051\./{f=1;print;next} f&&/^##+ /{exit} f' <pack>`) and the plan sections its Context line names; find them with `grep -n '^#' <plan>`. Never load the whole plan, the whole pack or its JSON. Read the source files the card names, and widen only for a specific question.
- Do one task at a time, on a branch `feat/<task-id>-<slug>` from current `origin/main`. Work that already satisfies a test scenario is verified, not rewritten.
- The card's Files list is the expected scope, not a fence. Add a helper, test or call site when the task needs it, and name it in the PR. Stop and ask only when a change affects acceptance, a public contract, architecture or source ownership.

### Keep it simple
Load the `karpathy-guidelines` skill when writing, reviewing or refactoring code. Its "if uncertain, ask" rule yields to "Decide, don't ask" below.
- Build what the card asks for in the simplest form that works. Add no guard, fallback, retry, option or layer for a case that no card, test scenario or real caller needs.
- Validate at real boundaries only: worker-writable data, external processes, the network, files from outside the repository and owner input. Trust typed internal callers, and do not re-check what one owner already enforces.
- Prefer existing code and existing tools (git, the platform) over hand-written replacements. Remove what your change made unused. Mention unrelated dead code; don't delete it.
- Tests cover the card's scenarios and the bugs actually found, not hypothetical misuse.
- A review finding that only asks for more hardening, with no concrete reachable scenario in current code, is a P3 residual. Record it and do not implement it.

### Fixing
- Fix a defect at the owner the cited KTD names, not at each call site. If the same guard would go into many places, stop and raise a design question.
- Fix only what the task needs or broke. A focused-test failure listed in `docs/known-failures.md` with a matching test and error is pre-existing. Reproduce any other suspected pre-existing failure at the base commit in a throwaway worktree, and add confirmed ones to the list.
- Never weaken a legacy test; legacy mode behaves exactly as before.
- Fix a failure with a verified cause directly. Verified means it was reproduced, or a failing test or a direct trace names the responsible line or decision. Keep a test that fails for that cause, fix it, rerun, and record the cause and evidence in the PR. The full `spec-debug` workflow is only for failures whose cause is unknown. In this repository this overrides the `spec-debug` entry rule in the managed block above.

### Review
- **Core code (owner directive, 2026-10-26)** is `engine/config/isolation/`, `engine/packages/daemon/src/adapters/worker-launch*.ts`, credential handling, and `engine/packages/daemon/src/domain/team-workspace.ts`, the one place the control plane reads worker-written files. Everything else is non-core, including authority, admission, the mailbox and `contracts/`.
- **Review size:**
  - a docs-only change gets no reviewer;
  - a non-core change under 100 changed lines (`git diff --numstat <base>`, tests included) gets one reviewer for one round, plus one confirmation of any P0/P1 fix;
  - any other non-core change gets one reviewer;
  - a core change gets two reviewers on the same frozen candidate, and fixes start only after both have reported.
- **Reviewers:** `gpt-6.1-sol` first. The second is `ds/gpt-6-astra`; until the owner restores the DeepSeek mapping, use `claude-sonnet-5-5` as a report-only subagent instead. Give every reviewer `engine/config/team/roles/reviewer.md` and `engine/config/team/core.md`. The brief adds facts only: the card, cited KTD excerpts, the candidate or fix delta, the round number and earlier findings with their dispositions. `docs/operations.md` "Reaching reviewers" says how to call them. Never print or persist keys.
- **Lenses:** correctness, testing and security always run. Other lenses run only when the diff touches what they check.
- **Rounds:** two per task. After round 2, P2/P3 findings become residuals. Up to two more rounds run only for open P0/P1 findings, and only while their count falls. A P0/P1 still open after that goes to the owner, and an owner-decided fix gets one more round. From round 2 on, the reviewer sees only the fix delta (under about 40 KB), and the reviewer that raised each finding confirms it. A new finding in code the delta did not touch is a residual unless it is a reproduced P0. A fix round changes only what the findings require.
- A transport failure (HTTP 524, a dropped stream, or a call running over 20 minutes) is not a round; retry it once. Skip the final-branch review when the branch tree hash equals the reviewed candidate's.
- **Standing review-dispatch grant (owner, 2026-10-17).** Dispatch isolated, report-only reviewer subagents without asking, and record `worker_dispatch_authorization: authorized`. An inline fallback never closes a required gate.

### Verification
- Every task verifies with the focused tests for the code it touched and the touched package's typecheck. Run no package suite or full suite per task, even where a card or the plan names one. The full suite runs once, at project wrap-up or when the owner asks; see `docs/operations.md` "Full daemon suite".
- Make at most two fix-and-rerun cycles per failing check.
- A repeat-run proof uses the card's run count, else 20 runs. An investigation with no card-named target stops after 30 minutes: report what was measured, land what is proven and record the rest.

### Decide, don't ask
- Decide a question yourself when the card, the plan sections it cites, these rules or the launch prompt settle it, or when the choice stays within the card's purpose, done signal and contracts. Record the reason in the PR and continue. Unattended runs never ask; they take the simplest option these rules allow.
- Ask the owner only for:
  - scope beyond the card's purpose;
  - a change to acceptance, a public contract or architecture;
  - a grant these rules do not give;
  - one of the stops below.

  Batch the questions, and keep working on whatever they do not block.
- Stop and report when:
  - the plan conflicts with the current source;
  - a required tool or credential is missing;
  - a P0/P1 survives the review rounds;
  - the remaining work is clearly as large again as the budget.
- **Budget guide per task:** about 3 runs, 6 slices, 1,200 changed lines and one scope amendment, summed across sessions. Finish nearly-done work that runs past it, and record the overrun. A resumed session reuses evidence whose source hashes still match.

### Done and delivery
- A task is done when:
  - every test scenario is covered by a passing test;
  - the focused tests and the touched package's typecheck pass;
  - the required review has closed.
- The PR description is the report: changed files, test commands with counts, pre-existing failures, residuals, decisions and reviewer verdicts. Write no separate intake, preservation, budget or handover files. Keep logs under `.spec-first/workflows/spec-work/multi-agent/<UTC>-<task>/` only when they back a claim in the PR.
- Before the PR says a test fails without a line, revert that line and run the test. If nothing fails, call the line defence-in-depth, not covered behaviour.
- Do not edit `docs/plans/` or `docs/tasks/` during a task, except to regenerate the pack after drift.
