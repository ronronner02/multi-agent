## Language and Governance Policy
**Language setting:** `English / 英文`
Language rules are an absolute hard-execution requirement: unless the current request explicitly asks for another language, translation, bilingual output, or preserved source text, all newly generated natural-language content intended for the user must be in English.
Scope covers responses, status updates, clarification questions, summaries, reviews, generated documents, requirements, plans, tasks, change notes, commit messages, and PR text.
Code identifiers, commands, paths, config keys, environment variables, API names, protocol names, logs, tool output, and quoted material may remain in their original language; any new explanation, conclusion, or surrounding guidance must follow this language setting.
The source language of skills, agents, templates, historical context, or examples must not override this setting; new code comments also follow this setting and explain only non-obvious intent.
### External Output Privacy and Attribution
Never automatically add workflow, tool, skill, agent, model, vendor, or generation-method names, attribution, links, footers, badges, or promotional text to newly generated user-facing or external artifacts, including pull requests, issues, commits, release notes, changelogs, reports, plans, specifications, and business documents.
Never automatically add `Built with`, `Generated by`, `Powered by`, AI authorship, or co-author trailers. Add a specific attribution only when the user explicitly requests that exact attribution in the current turn.
### Workflow Entry Governance

## Execution Rules for Agents

These rules apply to every agent working in this repository. The owner reset the project on 2026-10-31: build the MVP first, then iterate (`docs/amendments/2026-10-31-mvp-reset.md`). These rules override a workflow skill's defaults and any review or suite instruction in a plan or task card. Reusable standards are in `docs/development-standards.md`; operational detail is in `docs/operations.md`.

### Current focus: the Windows-native desktop
- The active plan is `docs/plans/2026-11-09-001-feat-windows-native-desktop-plan.md` (owner decisions, 2026-11-09). Work its units in the plan's wave order. Each unit is one PR, and `main` stays green after every unit.
- The direction is Windows-first and portable:
  - the Electron desktop owns the engine, and the browser is an optional viewer;
  - agents run as direct child processes, with no tmux and no WSL;
  - the Multi-Agent legacy and the TUI are deleted, and the product is renamed Multi-Agent;
  - a thin `multi-agent` CLI remains.
- **Deferred:** hardened isolation, macOS support, release publication and code signing. T038 is cancelled with the WSL path.
- A unit is done when its focused tests, typecheck and smoke pass, and its Windows verification ran wherever the unit calls for one. Don't harden, generalize or polish a unit while the next one doesn't yet work end to end.

### Environment
- The shipped target is native Windows 10/11 x64 with Node 22 or 24 and Git for Windows. The engine also stays portable to Linux, and CI runs both. Until the plan's tmux deletion units land, the legacy Linux path still needs tmux. The default path needs no admin rights, no special users and no host provisioning.
- Code, scripts and CI contain no user- or machine-specific paths, hosts, proxies or credentials. Use the per-user config and state directories.
- Each task works in its own worktree, created from current `origin/main`, and never in another task's checkout. Scratch files and extra clones go under one folder per task, and are removed when the task lands.
- Tests run with stdin detached (`</dev/null`), one vitest process at a time, `--maxWorkers=2`. Leave no vitest process, tmux server or daemon fixture running when you finish.
- **On the owner's machine:**
  - OS-neutral units work in worktrees of WSL `/home/leo/src/multi-agent` under `/home/leo/scratch/<unit>/`. Units that need Windows verification work in worktrees of the Windows clone `D:\ma\repo` under `D:\ma\<unit>`; keep the path short because of Git's worktree length limit. Never edit `D:\Multi-Agent`, which is a read-only mirror.
  - The C: drive is nearly full: create nothing on it. Point `TEMP`, `TMP` and `npm_config_cache` at `D:\ma\tmp` and `D:\ma\npm-cache` in every Windows command, and put temp homes, Electron user data and fixtures under `D:\ma\tmp`.
  - Node is at `/opt/multi-agent/toolchain/node/bin`.
  - Scratch goes under `/home/leo/scratch/<task-id>/`.
  - From Windows, run scripts with `wsl.exe -e bash <file>`, never `wsl.exe -- bash -c '…'`: its outer shell expands `$VAR` to an empty string.

### Keep it simple
Load the `karpathy-guidelines` skill when writing, reviewing or refactoring code. Its "if uncertain, ask" rule yields to "Decide, don't ask" below.
- Build the simplest form that works. Add no guard, fallback, retry, option or layer for a case that no slice, test or real caller needs.
- Validate only at real boundaries: worker-written data, external processes, the network, files from outside the repository, and owner input. Trust typed internal callers.
- Prefer existing code and tools over hand-written replacements. Remove what your change made unused. Mention unrelated dead code instead of deleting it.

### UI
- Follow `docs/development-standards.md` section 9 for every Web UI and desktop screen: no redundant labels, captions or helper text; hierarchy, spacing and a clear primary action explain the screen; extra information goes behind an info icon with a tooltip. Keep form labels, accessible names and the consequence statement on dangerous or irreversible actions.

### Fixing
- Fix a failure with a verified cause directly. A cause is verified when the failure was reproduced, or when a failing test or a direct trace points to the responsible line. Keep a test that fails for that cause, and record the cause in the PR. The full `spec-debug` workflow is only for failures whose cause is unknown; in this repository this overrides the `spec-debug` entry rule in the managed block above.
- A failure listed in `docs/known-failures.md` with a matching test and error is pre-existing. Never weaken a legacy test.

### Verification
- Every change runs the focused tests for the code it touched, the touched package's typecheck, and `npm run smoke` in `engine/` once that script exists. CI runs the smoke set on every PR.
- The full suite runs only before a release or when the owner asks.
- Before a PR claims a test fails without some line, revert that line and run the test.

### Stop rules
Stop and report instead of looping when:
- a slice grows past twice its estimate;
- the same fix fails twice;
- an investigation runs 30 minutes without a measured lead;
- the change needs a new public contract or architecture;
- a required tool or credential is missing.

### Decide, don't ask
- Decide a question yourself when these rules, the slice's purpose or the launch brief settle it. Record the reason in the PR and continue.
- Ask the owner only about scope beyond the slice, a change to a public contract or architecture, a grant these rules don't give, or one of the stops above. Batch the questions, and keep working on whatever they don't block.

### Review
- The orchestrating session reviews every PR: it reads the diff, runs the slice's demo and checks smoke CI. Implementers do not dispatch their own reviewers.
- A change to credential handling, `engine/packages/daemon/src/domain/team-workspace.ts` (the reader of worker-written files) or the hardened isolation path also gets one independent, report-only reviewer. It runs one round, plus one confirmation of any P0/P1 fix. Give every reviewer `engine/config/team/roles/reviewer.md` and `engine/config/team/core.md`; `docs/operations.md` "Reaching reviewers" says how to call one.
- A finding that only asks for more hardening, with no reachable scenario in current code, is recorded as a P3 residual and not implemented.

### Done and delivery
- The PR description is the report: what changed, how to see it work, the test commands with counts, decisions and residuals. Write no separate report files.
- **Standing delivery grant (owner, 2026-10-16).** Commit the scoped files, push the feature branch, and open or update the PR without asking. Once the review is done and CI is green, land it with a rebase merge.
  - Never force-push, rewrite published history or push to the default branch.
  - A release, deployment or Windows export needs its own grant.
- Commits and PRs carry no tool or AI attribution. Don't stash, reset or revert unless the owner asks.
- Record decisions in `docs/amendments/`. Don't edit `docs/plans/` or `docs/tasks/` during a slice.
- The T038 live grant is suspended while T038 is parked.
