# 2026-11-04: The lead slice (C3)

**Decided by:** the implementer of slice C3, under the owner's standing grants in `AGENTS.md`
and the 2026-11-02 MVP scope amendment, decision 3, bullet C3.

This records what C3 settled that the plan, the amendment and `AGENTS.md` did not already
state, so a later reader does not have to re-derive it from the diff. The plan text and the
derived task pack are not edited.

## The lead's request channel

The open question in C3 was how a lead agent, launched by the direct launch under
`workers.isolation: none`, **requests** its implementer tasks. The brief's order of
preference put "an existing request path the lead can already reach" first and "a structured
result the daemon reads after the lead's attempt ends, validated at that boundary" second.

**Decision: the second.** No existing path reaches an agent that can admit work, and the two
that look close are both wrong for this:

- **The mailbox capability** (`team_seat_mailbox_capabilities`, `WorkerMailboxBridge`) is a
  *message* channel. A lead could message the owner, but a message is not a task batch: the
  owner would still have to retype the decomposition, and the daemon would still have to trust
  whatever text arrived. C1 already has the right shape for "an owner-approved batch of tasks",
  and a message would be a second, weaker copy of it.
- **The control surface** (`/api/team-control/...`) is owner-authenticated for every verb that
  admits anything. Letting a lead reach `tasks/create` or `growth` would need a new
  agent-facing credential with write authority — a public-contract change the brief says to
  stop and report rather than build. It would also violate the plan's "agent capabilities can
  request but never grant approvals": a lead that could call the admission path directly would
  not be requesting.

So the lead writes **one structured file into its own candidate tree**,
`lead-proposal.json`, and the daemon reads it through `readWorkspacePath` — the same pinned,
no-symlink-follow, size-bounded reader every other read of worker-written output uses. Nothing
new is exposed to the agent: it already writes its candidate tree, which is what an
implementer does. Nothing the lead writes is admitted by the read.

## How owner approval gates the lead's tasks

The read produces a `LeadTask[]`; it does not produce tasks. `POST
/runs/:runId/tasks/:taskId/proposal` re-reads the file at the boundary, and
`PlanGovernance.proposeLeadTasks` turns the batch into **one pending `scope-change` approval**
whose payload is `{ change: "lead-proposal", tasks }` and whose `target_digest` is the hash of
that exact batch. That is C1's shape, reused: the owner's `approvals/decide` call is the only
thing that admits anything, and `applyLeadProposal` then writes each task through the one
admission path (`admitTask`) a start, a run growth and a C2 review task already use.

The binding is **not** replaced and the run is **not** suspended. C1 growth suspends because
it changes the approved plan, repository or limits; a lead's decomposition stays inside the
scope the owner already approved, so re-approving the binding would be asking twice for the
same decision. `growthTasks` still validates the batch — role, paths inside `writePaths`,
dependency graph, the 100-task ceiling — so an out-of-scope or cyclic decomposition is refused
before any approval row exists.

Two extra refusals live at this boundary because the lead chooses seats from a roster:

- Every proposed seat must declare the `implementer` role on the run's rig. The roster lists
  roles too, and handing a reviewer or lead node an implementer assignment is not something a
  lead's text should be able to do.
- A start naming a lead refuses when the rig has no implementer seat to delegate to
  (`lead_roster_empty`). The activation's manifest also refuses an empty roster, so this is
  the earlier, clearer refusal rather than a launch that fails later.

## The lead's context

The manifest already built the lead's protocol, roster and run-instruction entries
(`ContextInput.lead`, `leadProtocol`, the `protocol`/`roster`/`run` kinds) and
`LeadActivation` already refused a context that was not the lead's. What was missing was a
production caller: `WorkflowRuntime.projectAttemptContext` now projects the `roster` and `run`
entries when the attempt's role is lead, and the launch composition in `startup.ts` builds the
activation (`leadActivation`) from the rig's own seats.

The protocol entry is not written twice: `roleInstructionEntries("lead")` already projects
`config/team/lead-protocol.md` as the lead's charter, and the manifest requires exactly one.

**Run instructions may span lines.** The manifest's `text()` helper refuses control characters,
which a prose instruction cannot satisfy. The instructions are validated by their own rule —
non-empty, at most 8 KiB, no control characters except a line break and a tab — and every other
lead field keeps the stricter rule. This is the only relaxation, and it is stated where it
applies.

## `maxSessions`

The default binding's limit goes from **1 to 2**.

- One was not enough for this slice. The lead's own attempt is live while it reads the goal
  and writes its decomposition, and the work that follows is a second live session; at one, a
  second seat could never start while the first was still recorded running.
- Three is the contract's ceiling and C2's review loop can reach it, but a review round starts
  only after the implementer's attempt is observed stopped, so this slice never needs a third
  concurrent session. The limit is raised only as far as the slice needs, which is what the
  brief asks for.

The limit is a fact about the *binding*, so a run approved before this change keeps 1. That is
deliberate: raising it is a `limit-increase` escalation, not something a code change grants.

## What a lead may not do

Unchanged and re-proved: the lead has no `write-assigned-tree`, `submit-review` or
`record-acceptance` permission, and `prepareTeamAssignment` still refuses those for the role.
The dependency graph now exempts the lead from claiming write paths for the same reason it
exempts a reviewer — neither writes an assigned tree, so neither can overlap another task's
claim. Its dependency edges still count.

## Surfaces

- `rig team start <goal> --lead <seat>` (opt-in; without it the start is byte-for-byte the
  pre-C3 start) and the Web UI "New task" form's optional lead field.
- `rig team proposal <run-id> <task-id>` reads the batch; `--decide approved|rejected` records
  the owner decision and, on approval, the tasks are admitted and dispatched.
- The Web UI needs no new screen: a lead proposal is a pending `scope-change` approval, so the
  existing decision card already lists it and the existing dialog already renders its tasks.

## Residuals

- **One reviewer seat serves one live task at a time.** That is C2's own rule (the launch
  composition refuses a seat with two live tasks), not a C3 limitation, and the demo takes two
  reviews in turn rather than in parallel. A run with several implementers and one reviewer
  therefore reviews serially.
- **A lead that proposes twice.** A second read of the same file with the same idempotency key
  replays the first approval; a different key with the same batch is refused as a duplicate.
  A lead that rewrites its file after the owner decided produces a different batch and a new
  pending approval, which the owner can reject. There is no "supersede" verb; C1 does not have
  one either.
- **No automatic dispatch of the lead's own task.** The start dispatches it exactly as it
  dispatches an implementer task; the proposal read is a separate owner action, so the owner
  decides when to look.
- **No migration.** The lead seat is read from the run's own lead task row and the roster from
  the rig's nodes, so this slice adds no column and no table. It is therefore unaffected by
  `108_cancellation.sql`'s `team_runs` rebuild and collides with no later migration number.
