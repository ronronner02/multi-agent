The owner requested an ordinary local launch without repeated pairing, the visible
ink-wash skin, and a working desktop whose task visibility matches the original
reference. The owner also requested a pinned small open-source baseline, recreated
by the product's own team and compared before claiming autonomous delivery.
The current projects, sign-ins, form state, and previous installation remain
preserved. The normal launch entry may be updated to the repaired desktop.
This does not lift the separate uncommitted/unmerged acceptance hold.

## Connection correction

An ordinary launch selected a different configuration profile from the working
engine. Store only the existing non-secret runtime-profile paths in desktop
settings, keep credentials outside the renderer, and use the same profile for
engine startup and native pairing. A failed pairing stays on the connection
screen with Retry. A successful desktop renewal preserves the mounted application.
Only a pre-action authentication rejection may cause one bounded replay; network
or business failures never do. Explicit disconnect takes precedence over late
requests and in-flight renewal. The authentication policy and session lifetimes
are unchanged. Independent credential review and native reopen evidence remain
separate gates from unit checks.

Design north star: a focused engineering workbench with a recognizable ink-wash
backdrop, readable opaque evidence panels, and one selected task whose work and
review are visible beside the list. Retain the approved typography, semantic
colors, keyboard access and dark/light preferences.

The previous media opacity and overlay reduced the artwork to about 1.2 percent
contribution. Increase its visible contribution in the canvas gutters and expose
a deliberate artwork area in the overview heading. Replace the opening-dot
poster with a meaningful frame from the existing unmodified loop. Keep pause on
blur/hidden and still-only rendering for reduced motion.

Reuse the existing task detail, progress, timeline and review evidence. Selection
must remain run-scoped and work with keyboard navigation and deep links. Filtering
uses published stages and readable names; no queue-state reclassification.
The board is retained as another view. On narrow screens, reflow the inspector
without covering list controls or introducing horizontal page overflow.

The owner subsequently approved the additive owner-only task description,
declared acceptance criteria and workspace/branch read fields. Extend the existing
read projection and inspector using their authoritative task and workspace records;
do not synthesize requirements or workspace identity from logs. Scheduling,
approval and write interfaces are outside this presentation change.

The task description and separately headed acceptance section are inert, redacted
text bounded to 2,000 characters each, with truncation disclosed. Only explicit

review outcomes. Existing free-form briefs remain supported without a new write

not acquired on read; after restart it remains unavailable until that owner has

labelled separately from the task worktree. No filesystem read or new Git process

## Baseline evaluation

`https://github.com/gabrielecirulli/2048`, pinned to
`478b6ec346e3787f589e4af751378d06ded4cbbc` under its MIT license. Keep its original
source and license separate from the fresh recreation workspace. Preserve all
required license notices for reused assets. Do not upload owner files or create
additional remote repositories as part of this evaluation.

Freeze the feature checklist and scoring checks before generation: movement and
merge rules, score and best score, new game, keyboard and touch input, win/continue
and loss/retry, persistence, responsive layout, and a bounded accessibility
comparison. Test the original with the same applicable checks. Improvements must
pass additional observable checks without reducing baseline feature parity.

Run generation through the product's normal lead, approved plan and roster,
worker, reviewer and integration path. Record candidate-worktree identities,
concurrent attempts, review/rework, message correlation, and recovered results.
A manually implemented replacement, a synthetic screenshot, or a successful build
is not evidence of this autonomous flow. Keep failed attempts and scores rather
than repeatedly running until an unexplained green result appears.

## Long-profile mailbox correction

The live recreation run reached no agent attempt: its 123-byte mailbox endpoint
exceeded Linux's 107 usable pathname bytes, and startup repeated the same error.
Extend the existing unisolated-root owner and add its focused regression test.
Keep short-profile endpoints unchanged. For a deeper profile, only the transient
mailbox moves to a short, per-user/per-profile private temporary directory; the
database, assignments, plan bindings, candidate records and credentials keep their
existing owners and identities. Count UTF-8 bytes, retain full attempt identifiers,
and reject non-private or substituted temporary roots. This changes neither the
public API nor the hardened launch path. Preserve the failed startup evidence and
resume the original run instead of starting a replacement benchmark.

## Direct-launch terminal identity

The two live implementers used separate worktrees and native sessions, but their
stored direct-launch receipts described the terminal server as `/tmp` instead of
the actual profile-specific socket. The existing unisolated-start test now compares
the receipt with tmux's own `socket_path` observation and reproduced the mismatch.
Use the same socket-path resolution already present in the managed launch owner,
without changing that owner or the selected terminal server. Existing running
attempts and historical receipts are not rewritten; subsequent launches record the
correct socket identity. This fixes evidence accuracy, not a demonstrated
cross-task write or cancellation incident.

## Reviewed dependency handoff

The live recreation run started its final assembly task while a prerequisite's
review was still running. The queue correctly recorded worker completion, but the
shared dependency gate treated validated completion as publication. The integration
owner had not yet put those files on the run branch, so the assembly worker found
only the earlier prerequisite and correctly reported a blocker without writing.

For runs with a reviewer seat, an implementer dependency now also requires its
recorded integration commit. The existing integration owner records that commit
after review approval and applying the patch; no new state or public contract is
introduced. Legacy runs without a reviewer retain validated-completion behavior,
and handoff custody still follows the successor. Admission applies this gate before
creating a dependent candidate. A real-Git regression covers pending review,
approval before integration, the actual prerequisite file in the admitted workspace,
and a daemon-object restart. Existing attempts and review records remain intact.

## Retired-task ownership during recovery

The same run's lead attempted the correct recovery: drop the empty blocked
assembly task and admit a fresh task over the same approved files. Admission
rejected that proposal because it checked the old task's paths before applying
the validated drop, then kept historical path claims even after a separate drop.
The fallback rework retained the earlier base and hit the same missing files.

The existing task-growth graph now releases write claims for validated drops in
the current transaction, and for already dropped or integrated tasks whose queue
state is done and which have no live attempt or unresolved native launch. Their
identities, edges, evidence and attempts remain recorded. Pending review,
unintegrated work and active rework continue to reserve their files. This also
permits ordinary follow-up improvements over previously integrated files without
creating a replacement run. No candidate files are deleted or manually supplied,
and no plan scope, public API or permission grant changes.

## Seekable skin delivery

Decoded-frame checks reproduced the entrance returning after a seek. The UI asset
server answered byte-range requests with `200` and no range metadata; the browser
clamped a seek to zero. A direct request to the working daemon confirmed the same
response, so this was not only a fixture discrepancy.

Extend the existing UI file-response owner for MP4 assets with single byte-range
responses, content lengths and range availability. Preserve full-file reads,
non-video responses, managed-page admission and the UI-off gate. Unsupported or
unsatisfiable ranges return `416`; HEAD retains headers without a body. The trusted
bundled asset still uses the existing bounded-by-file read; this adds no file access
surface or dependency. Verify open-ended, suffix, clipped-end and invalid ranges,
then observe decoded portrait frames across multiple real playback boundaries.
