# Project discussion and approved document versions

## Owner decision

The owner approved five product capabilities on 2026-11-08: optional exploration notes, confirmed project requirements, plans derived from confirmed requirements, a persistent desktop document center, and execution bound to the approved document versions. This is product behavior, not a claim that the development-time workflow catalog is operational in the product.

## Implementation decisions

- **Extend** the existing run, lead conversation and governance transaction. Opening project chat still creates no record or execution task. The first message creates a planning record. New desktop planning records opt into versioned documents; historical records retain their existing behavior and are not backfilled with invented documents.
- **New persistence within the existing owner:** immutable document content snapshots, per-record stage/confirmation pointers, and idempotent turn-capture receipts in the existing database. The run remains the conversation and execution owner; project history groups its documents. Brainstorm is optional. Requirements and plan are required for document-governed execution.
- **Compose** the existing bounded candidate reader with lead turn completion. Snapshot documents before any queued continuation. Read failures remain visible and block confirmation; a read endpoint never creates a version. A plan snapshot names the requirements version it was derived from.
- **Extend** the existing owner commands for stage changes and exact-version confirmation. Stage changes do not approve execution. Requirements confirmation is required before requesting a plan. Changing requirements invalidates the dependent plan confirmation; all changed requirement bytes are conservatively treated as requiring confirmation rather than guessing semantic significance.
- **Extend** the plan binding with optional immutable document pins. Validate the displayed version IDs and hashes, current source bytes, roster digest, idle turn state and run version before committing a plan. Enforce the pins again at assignment admission and immediately before a direct launch, including continuations. Historical bindings without document workflow remain compatible.
- A request to revise approved documents closes new execution admission immediately. If turns are still active, preserve the approved bytes and wait for their recorded stop before opening revision. Replanning supersedes unfinished execution tasks, retains finished results and history, and requires a fresh approval. Resume does not restore an obsolete document approval.
- Adapt the exploration, requirements and planning purposes and output sections from the referenced project into stage-aware lead instructions. Do not install or claim operation of unrelated workflows. The desktop exposes stage actions, document content, version comparison, exact confirmation and a discussion link using the existing visual tokens.
- Preserve the owner's selected lead and child-model allowlist. Reconcile idle seats by role when the approved roster changes client; clear stale continuation identity. Busy seats retain their client until stopped.

## Iterative conversation follow-up

The owner clarified that planning must behave as a discussion: focused questions with choices, free-text refinement, then a plan and tasks, followed by explicit execution approval. Reuse the existing lead question file, decision rows and `answerTo` chat command in planning rather than introducing another protocol or a terminal-interaction bridge. Planning instructions ask one material question at a time, explain the recommendation and trade-off, and wait for its answer; already-settled details do not require ceremonial questions. New planning assignments declare the existing lead conversation metadata path. Question/answer context is carried into the next native turn, and questions and answers remain in the existing conversation history.

The composer can answer a pending question in prose. Such an answer never invokes a document or execution approval, even when its text resembles an approval shortcut. An unanswered question blocks document confirmation, stage transition and execution approval at the governance boundary as well as in the desktop. Explicit requests to prepare requirements or generate a plan use the existing stage command, retain the owner's text, and preview that execution remains stopped. Free-form discussion remains discussion; the built-in stage controls are always available. No claim is made that arbitrary prose is semantic authorization.

The projected lead protocol is version 4: its higher-priority planning rule now permits the named stage documents and the existing question metadata. Its prior plan-and-roster-only rule contradicted the stage instructions. Protocol and composed-context regressions cover the updated projection and instruction-size limits.

Installed acceptance exposed a repeated task-name collision when a project retains multiple planning records. Extend the existing in-process launch selector with its run ID and filter both IDs before the ambiguity limit. An explicitly missing run/task never falls back to the only task on a seat. Native continuations are read from the selected run/task's stopped receipt, not the shared seat's most recent conversation token; switching project records must not continue the other record's native chat. No existing records are canceled to make the selector unique.

Live dialogue ended exploration by offering either requirements or a plan even though requirements confirmation is required first. Stage instructions now name the next valid owner action: prepare requirements, confirm requirements and generate a plan, then confirm the plan and separately approve execution. The stage contract test covers these prompts; runtime dialogue remains a separate acceptance check.

Native desktop navigation exposed a sibling React key collision: the document screen and chat panel both used the bare run ID. Namespace their keys and extend the route regression to enter and leave Documents repeatedly while retaining the same chat composer. Historical-document discussion now includes the selected immutable snapshot and identifies the latest version separately; it does not request reverting current decisions. Context is bounded to 32,768 characters, with an explicit excerpt label when larger, leaving room for the owner to describe the change within the existing chat limit. No document confirmation or execution approval is inferred from this reference text.

## Residual acceptance repairs

The owner requested completion of the disclosed residual fixes. Explicitly pre-roster records keep their original combined plan-and-execution approval contract when the same action is typed in chat. The typed action records the owner message without inventing a displayed plan hash. Modern roster- or document-governed records still require that hash, and any supplied hash is checked even on a legacy record. Missing chat-read evidence remains distinct from an explicit legacy null proposal. No historical documents or rosters are backfilled.

A route-level reproducer showed that a failed periodic account read unmounted the project subtree, closing chat and discarding its unsent draft. Retain that already-verified subtree hidden while the existing failure gate is shown; restore it on a successful recheck. A cached account at first mount is not verification, and a confirmed sign-out still removes the subtree. No credential, account, approval, or navigation command is changed. This reproduces a concrete loss path, not a retrospective attribution of the earlier uncorrelated native closures.

A stop-boundary reproducer showed that committing an attempt's terminal state before saving its documents excluded that turn from all later sweeps. Persist the document snapshot after observing native exit but before recording the stop. An interruption before the stop remains eligible for the existing sweep; after it, the snapshot is already durable. The existing per-attempt receipt prevents duplicate capture, including when candidate bytes change before restart. An interrupted capture that has not saved a receipt leaves the attempt pending observation and does not offer its slot for dispatch. Unreadable files retain the existing durable, visible error behavior. This changes no document-read endpoint, approval, schema, or historical capture: old stopped attempts are not replayed against today's mutable candidates.
